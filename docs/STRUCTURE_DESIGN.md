# v2 架构基线（所有后续 agent 先读）

本仓库是 K230D/K230 RT-Smart 的**用户态业务代码仓库**，不是固件工程，也不负责烧录或修改板端 BSP。当前分支只有构建骨架、配置和设计文档；`src/`、`include/` 下的业务模块需要后续任务逐步建立。文档中出现的源码路径均为目标路径，不表示该文件当前已经存在。

## 1. 工况与目标

最终设备是无动力抛体/滑翔体，使用相机识别引导灯和装甲板，结合 IMU、姿态控制和舵面执行机构完成末段导引。主要工况分为：

1. **启动/重捕获**：不知道目标位置，必须全图扫描并用时间一致性确认，宁可暂不输出目标，也不能把坏点或反光当成目标。
2. **跟踪/接近**：目标尺寸随距离增大，使用预测 ROI 和尺度状态降低扫描开销，同时在丢帧、出框和干扰物出现时可退化到重捕获。
3. **飞行控制**：外环修正航向/落点，内环跟踪姿态，末段在可行性约束下逐渐转向终端姿态，不能把“机头对准目标”误当成“速度方向命中目标”。

视觉、IMU、控制和录像必须以时间戳、有效位和明确的所有权连接；任何一层都不能用默认值掩盖数据失效。

## 2. v2 的分层和依赖方向

```
L4  领域/策略层（纯 C++）
    状态机、检测跟踪策略、观测器、控制律、参数策略、诊断事件
             ↓ 依赖抽象接口，不认识 SDK、文件系统和线程库细节
L3  设备/运行时抽象（纯 C++）
    相机、IMU、舵机、计时器、存储等接口；通过构造注入总线和资源
             ↓ 由适配器实现
L2  防腐层 ACL（C++ 适配器）
    把 K230 SDK 的 C API、句柄、返回码、缓存同步和所有权翻译成稳定接口
             ↓ 只在边界处包含厂商头文件
L1  BSP/HAL/MPP（厂商 C）
    SDK 原始头文件和库；不在本仓库中重写或“美化”
```

识别热路径、帧池和 MPP/VENC 数据通路是一个受控例外：采用 **C 数据面 + C++ 控制面**。C 负责固定布局、像素循环、缓冲区状态和 C ABI；C++ 负责编排、策略、生命周期和错误决策。语言本身不是性能保证，必须用缓存行为、复制次数、分配次数和板端时序证明收益。
这套设计吸收领域驱动设计、依赖倒置和防腐层的共同原则：先让领域对象表达状态和不变量，再由边界适配外部系统；所有权、时间和错误都显式传递；硬件替换不应迫使算法层改写。外部仓库只能作为思想参考，不作为本仓库依赖或逐文件模板。

### 2.1 依赖规则

- 业务层不能包含 K230、MPP、POSIX 设备头文件，也不能直接调用 `ioctl`、`mmap`、`vb_*`。
- L3 只依赖自有抽象；驱动对象通过构造函数或 `create/init` 注入总线、时钟和资源。
- L2 是唯一允许翻译厂商返回码、处理 cache/DMA 同步和管理 SDK 句柄的地方。
- L1 保持 C；不得为了“统一风格”把厂商 SDK 改成 C++。
- C ABI 只使用固定宽度整数、指针和显式 POD；C++ 异常不得跨 ABI。
- 每个缓冲区必须写清所有者、读写方、有效期、stride、cache 属性和同步动作。

### 2.2 语言与错误契约

- C 数据面使用 C11，返回 `dart_status_t` 和输出参数；热循环中的“没有目标”是正常结果，用枚举/`bool` 表达，不伪装成错误。
- C++ 控制面使用 C++23 的 `std::expected<T, DartError>`（当前 CMake 已预留该标准），只在跨层需要携带失败原因时使用。
- `DartError` 必须定长、可平凡复制，不持有动态字符串；日志出口根据稳定枚举生成文字。
- 叶子函数只返回错误，不重复打印；能决定恢复动作的边界统一记录一次结构化错误。
- 初始化失败拆成 `create/init/start`，不在构造函数中打印、退出或抛异常。
- 在交叉工具链探针和实际链接验证通过前，不假设 `std::expected` 或 `-fno-exceptions` 可用。

## 3. 目录职责

实际布局（2026-10 更新，**不使用 `apps/` 目录**：可执行与库目标统一在
`src/CMakeLists.txt` 声明，模块子目录只放源码与 README）：

```
src/                        业务实现（C++ 编排 + C 热路径实现）
  detector/                 检测 + ROI（dart_detection，STATIC；detector.cpp + roi.cpp）
  recordor/                 灰度取证录像（dart_recording；单翻译单元 recorder.cpp）
  launcher/                 开机自启器（平台无关 C11）+ startup.list 清单母版
  vision/                   组合根：相机 + 识别 + 录像单进程 payload（dart_vision）
  control/                  目标：C++ 观测器、状态机、外环/内环和分配
include/                    与 src 对应的公共接口 + 固件侧库目标声明（camera/spi/imu）
cmake/                      交叉工具链配置（链接脚本取 SDK 的 libs/mk/link.lds）
scripts/                    构建（build.sh）与部署（deploy.sh / deploy-sdcard.sh）
docs/                       设计、标定、调试和验收契约
```

启动链路的完整设计（清单语义、所有权、日志布局、v1 教训）见
[`LAUNCHER_DESIGN.md`](LAUNCHER_DESIGN.md)。

目前不要因为目录在文档中出现就创建空壳文件；实现任务应先选择一个垂直切片，补齐接口、CMake、日志和验证，再进入下一个模块。应用之间不得共享可变全局状态。

## 4. 运行时数据流和所有权

```
VICAP/传感器（ACL）
       ↓ 带时间戳、stride、cache 状态的输入
固定帧池（C） → 二值化/扫描/ROI 测量（C）
       ↓ 目标坐标
检测与跟踪策略（C++） → 观测器/控制器（C++）
       ↓ 归一化力矩或舵偏请求
控制分配/舵机 ACL → 实际 PWM 与反馈
       ↘ 录像/取证数据面（固定队列、异步写盘）
```

- 运行态禁止逐帧 `malloc/free/new/delete`；启动期一次性申请并记录工作区高水位。
- 帧槽使用显式状态（例如 `free → captured → processing → queued → released`），一个时刻只有一个释放责任；不得依赖“看起来没有锁”来掩盖双重归还。
- 视觉线程不做文件 I/O；录像/诊断用有界队列，队列满时按策略丢样本并累计计数，不能阻塞采集或控制环。
- 时间统一使用单调时钟。视觉、IMU、控制和执行器记录采样时间、处理时间、数据年龄及 `valid/stale/saturated/gap` 标志。
- 观测、预测和控制失败时必须走安全退化路径；NaN、越界窗口、失效句柄不可进入舵面。

## 5. 验证策略

本仓库不做“为了主机测试而模拟整块板子”的工作。验证分三层：

1. **主机可重复验证**：只覆盖纯算法、固定尺寸数学、C ABI、状态机和错误传播；使用合成输入或显式 fake 接口，不向业务代码加入板端兼容分支。
2. **交叉构建验证**：用仓库的 RISC-V 工具链和 SDK 头/库检查 ABI、链接、段大小和 `-fno-*` 约束；构建产物是可拷贝到 RT-Smart 用户态的 ELF。
3. **板端验证**：验证 RVV、cache/DMA、MPP、真实曝光、传感器时序、舵机响应、录像和内存高水位。性能和视觉质量的结论只能来自板端日志/样本，不能由主机纳秒数替代。

每轮实现都应留下：变更范围、主机结果（若适用）、交叉构建结果、板端命令/参数、原始日志和失败样本。没有真实硬件时，文档只能写“待板端验证”，不能写成已通过。

## 6. Agent 工作顺序

1. 先读本文件，再读与任务相关的 `DETECTOR_DESIGN.md`、`IMU_DESIGN.md`、`CONTROL_DESIGN.md` 或 `VISION_C_REFACTOR_PLAN.md`。
2. 检查当前 Git 状态和实际目录；不要根据 v1 文档假设文件存在。
3. 先定义边界、数据所有权、错误/正常否定结果和日志字段，再写代码。
4. 修改一个垂直切片并在相应层验证；不要顺手重写 SDK、固件或无关模块。
5. 任何占位参数必须显式标为 `UNVALIDATED`，未经标定不能进入真实控制通路。
6. 文档中的历史数据只能作为假设或待复现实验，新增结论必须带来源、条件和日期。

## 7. 禁止事项

- 不恢复 v1 的 `apps/` 单一工程布局：可执行目标在 `src/CMakeLists.txt` 声明，模块
  子目录只放源码；也不要把 v1 的 `self_guiding_dart` 整体搬回来。
- 不要出现第二个持有 VICAP/VB 的进程：识别与录像必须在 `src/vision` 这一个 ELF 内
  串联（v1 实测多实例抢资源必死），清单里也不能放第二条 payload。
- 不要把外部仓库（包括 v1 或 RMCS）当作本仓库的依赖；只提炼设计原则并在本仓上下文重写。
- 不要用主机兼容层伪造 MPP/VICAP/VENC 行为；硬件假设要由 ACL 和板端探针验证。
